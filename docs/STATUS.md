## Bug #1 — FIXED: Wine's wineusb.sys doesn't register USB device interfaces
- Root cause: `dlls/wineusb.sys/wineusb.c` never calls `IoRegisterDeviceInterface`/`IoSetDeviceInterfaceState` for the USB PDOs it creates, so apps that gate "device present" on `SetupDiEnumDeviceInterfaces`/`CM_Register_Notification` (GUID_DEVINTERFACE_USB_DEVICE) never see arrival events, even though raw ALSA MIDI transport works fine.
- **Patch written and confirmed working** in `/home/deck/wine-src/dlls/wineusb.sys/wineusb.c` (adds GUID_DEVINTERFACE_USB_DEVICE registration in `IRP_MN_START_DEVICE`, cleanup in `IRP_MN_REMOVE_DEVICE`). Verified: `Control\DeviceClasses\{A5DCBF10-...}` now gets populated for our device (and all USB devices) after the patch.
- This is a legit, worth-upstreaming Wine bug fix.

## Bug #2 — FIXED (was actually a Wine-side bug, not purely Hotone's): crash in HTUSBTools.dll
- Crash: `EXCEPTION_ACCESS_VIOLATION` reading `[rcx+0xC]` with `rcx=0`, was 100% reproducible on every launch with the pedal connected, in every app version V1.0.0–V1.5.1, both under Proton and vanilla/patched Wine.
- Underlying app-side condition (still real, still exists in Hotone's closed-source code): `HTMIDIDevice::handleIncomingMidiMessage` (JUCE `MidiInputCallback` override) implements Hotone's own multi-chunk SysEx reassembly using a 14-bit length field read from the message. If the field is 0 it means "start of message" (allocates a fresh assembly-buffer object); if nonzero it means "continuation" and uses that buffer pointer **without a null check**. Confirmed via Ghidra decompilation of the real crash-chain functions in both V1.0.0 (offsets +0x24f8 etc.) and V1.5.1 (offsets +0x4d686 etc.) — identical bug pattern, different code offsets.
- **The actual trigger, found by instrumenting Wine itself**: `dlls/winealsa.drv/alsamidi.c`'s `handle_sysex_event()` receives raw ALSA `SND_SEQ_EVENT_SYSEX` chunks that do **not** respect message boundaries — a single logical SysEx from the pedal (e.g. 384 bytes) gets split by the ALSA raw-MIDI-to-sequencer bridge into multiple fixed-size chunks (e.g. 256 + 128 bytes) with no regard for where `0xF0`/`0xF7` fall. When the app's `MIDIHDR` buffer fills up before the real `0xF7` terminator, Wine correctly hands the app a fresh buffer to continue into — and that continuation chunk legitimately does **not** start with `0xF0` (it's genuine mid-message data). An earlier patch attempt in this same investigation (added to defend against a *different*, hypothetical "subscribed mid-broadcast" race) incorrectly treated **every** fresh buffer as needing to start with `0xF0`, silently dropping these legitimate continuation chunks — corrupting the SysEx image the app received and reliably reproducing the same null-pointer crash. Confirmed by direct trace logging inside `handle_sysex_event` (writes every raw chunk + `dwBytesRecorded` state to `/tmp/wine_midi_trace.log`) showing a 128-byte non-`0xF0`-prefixed chunk arriving with `dwBytesRecorded==0` right before the crash.
- **Fix**: added a per-source `expect_sysex_start` flag (`struct midi_src` in `alsamidi.c`) that is only `TRUE` on real device-open (`midi_in_start`) or after a buffer completed via a genuine `0xF7` terminator — **not** after a buffer-full rollover mid-message. The "must start with `0xF0`" guard in `handle_sysex_event()` now only fires when `expect_sysex_start` is true, so legitimate multi-buffer continuations pass through untouched while genuine mid-broadcast desync garbage is still dropped.
- **Verified working**: with the pedal connected, the app now runs 65+ seconds continuously processing real incoming SysEx traffic from the pedal with zero crashes, vastly outlasting the previous guaranteed <1-second crash. This is the current, best-known-good state of `dlls/winealsa.drv/alsamidi.c`.
- Debug instrumentation still present in the source (harmless, just logs to `/tmp/wine_midi_trace.log`): `trace_sysex_chunk()` helper + call site at the top of `handle_sysex_event()`. Safe to leave in or strip out before any upstream submission.

## Bug #3 — FIXED (worked around): app window rendered solid black
- Discovered by actually taking a screenshot (hadn't been checked visually before this point — all prior testing was headless via logs/crash reports).
- The `Ampero II` window was correctly created, mapped, positioned, and focused (confirmed via `xwininfo`/`xprop`) but its client area was always solid black, even with no pedal connected — unrelated to MIDI.

Genuine Microsoft `d3dcompiler_47.dll` (copied from a Steam game's bundled redistributable) fixed shader-compile warnings but not the black screen itself.
- **Fix (workaround, not a real fix to our own Wine build)**: abandoned trying to fix rendering in our own `wine-src` build. Instead switched the whole runtime to **Steam's Proton** (which has a mature, working DXVK+winex11 integration out of the box) and carried our two source patches over to it — see "Combined Proton + patches setup" below. Proton renders the UI correctly with zero changes needed beyond installing our patches.

## Bug #4 — FOUND AND WORKED AROUND: thread-race in Hotone's own HTUSBTools.dll, exposed by fast Wine sync primitives
- After moving to Proton and getting Bug #2's fix properly ABI-matched (see below), the app still crashed at the *exact same* `[rcx+0xC]` null-deref — but this time trace-logging proved the SysEx data Wine delivered was 100% clean and correctly formed (our Bug #2 fix was working perfectly). So this is a **different** trigger for the same underlying missing-null-check bug in Hotone's code.
- Hypothesis: Proton enables `ntsync`/`esync`/`fsync` (fast, tightly-scheduled synchronization primitives) by default. If `HTUSBTools.dll` has a genuine, unguarded data race between threads around that SysEx reassembly buffer pointer (plausible — the decompiled code shows no locking around reads/writes of it), tighter thread scheduling under Proton would make that race far more likely to manifest, while our own custom Wine build's slower/more serialized scheduling almost never triggers it (confirmed: dozens of successful runs there, zero crashes).
- **`WINEESYNC=0 WINEFSYNC=0` alone reduces but does not reliably eliminate this** — confirmed by repeated testing on V1.0.0: crashes still occurred sometimes with these set, including a *different* crash signature (`page fault on EXECUTE access`, not the usual `READ access to 0xC`), which pointed at a second, distinct race rather than one single bug.
- Checked whether Wine's own callback delivery could be the culprit: `dlls/mmdevapi/main.c`'s `notify_thread` is a single dedicated thread that processes queued MIDI notifications strictly one at a time in a simple loop (`MIDI_CALL(midi_notify_wait,...)` → `notify_client` → `DriverCallback`) — genuinely serialized already, not a source of concurrent-callback races. So the timing sensitivity is real but isn't explained by a missing lock on Wine's notify-delivery path.
- **Two concrete mitigations implemented in `alsamidi.c`** (both in the wine-11.0 worktree used for Proton, see below):
  1. **Throttle**: added `usleep(30000)` (30ms) right after `notify_post()` in `handle_sysex_event()`, giving the app's own MIDI-in callback processing more wall-clock time to finish before the next SysEx chunk is delivered. This alone took repeated crash-on-launch from "always" down to "occasionally," and was sufficient to reach the real working editor UI multiple times in a row.
  2. **Stale-callback-on-close fix** (this is a real, general Wine bug, not just a Hotone workaround): the `execute access violation` crash was immediately preceded in the log by `HTDevice disposed` → `ConnectionStatus.notConnected` — i.e. the app tearing down its device object. `midi_in_close()` stopped the ALSA recording thread but never drained notifications for its own device already sitting in the shared `notify_buffer` ring buffer, so a notification queued just before close could still be delivered afterward by `notify_thread`, calling back into an object the app had just freed (explaining the execute-access/use-after-free-shaped crash). Real Windows' `midiInClose` is documented to guarantee no further callbacks after it returns; Wine wasn't upholding that. Fixed by walking the pending ring-buffer entries under `notify_mutex` in `midi_in_close()` and setting `send_notify = FALSE` on any matching this device's `dev_id` before returning.
- With both of these applied, the app reached the fully working editor UI (visible presets, signal chain, effect browser, parameter knobs) repeatedly and reliably across many test launches on V1.0.0. Still not airtight — occasional stalls/hangs (see Bug #5) remain.
- The underlying missing-null-check in Hotone's own `HTUSBTools.dll` is still real and still there; these are Wine-side mitigations/fixes that make it very rarely observable in practice, not a fix to Hotone's binary itself.

## Bug #4b — FIXED FOR REAL (2026-07-26/27): binary-patched HTUSBTools.dll itself, no longer just a Wine-side mitigation
Follow-up session dug all the way into the actual crash instruction in the closed-source `HTUSBTools.dll` (V1.5.1) and fixed it at the source with a direct binary patch, rather than only reducing its odds from the Wine side.
- **Exact root cause, confirmed via Ghidra decompilation + disassembly of the real V1.5.1 binary**: `FUN_18004d640` ("putData", the SysEx reassembly buffer writer) is called from `handleIncomingMidiMessage` (`FUN_1800cdd30`) on two paths — the "start of message" path (`offset==0`) always mallocs a fresh 32-byte buffer object before calling it (safe), but the **"continuation" path (`offset!=0`, at file offset `+0xce398`/`+0xce39b`) passes `*plVar6` — the device's current reassembly-buffer pointer — into the call with no null check**. If a continuation-flagged chunk arrives while that pointer is still `NULL` (no "start" processed yet, or already consumed by the previous message), `FUN_18004d640` crashes on its very first instruction (`mov edx,[rcx+0xc]`) — this is the exact, long-observed `[rcx+0xC]` null-deref. The *caller* also unconditionally dereferences the same pointer again right after the call (`*(int*)(*plVar6+0x1c)`, at `+0xce3e6`/`+0xce3e9`), so a naive "just skip the call" fix still crashes one instruction later — confirmed by hitting exactly that second crash when the first patch attempt only guarded the callee.
- **The fix — two binary patches to `HTUSBTools.dll` itself** (V1.5.1; both `assets/HTUSBTools.dll` and `data/flutter_assets/assets/HTUSBTools.dll` copies inside a prefix need patching, e.g. `/home/deck/wine-proton-fresh/drive_c/Program Files/Hotone/Ampero II/`):
  1. **Callee guard** at `FUN_18004d640`'s entry (file offset `0x4ca40`, VA `0x18004d640`): the first 8 bytes (5 pushes: `40 55 56 57 41 54 41 55`) are replaced with a `jmp` into a code cave that does `test rcx,rcx` / re-executes the original pushes if non-null, or `xor eax,eax; ret` immediately (before any stack frame is built) if null.
  2. **Caller guard** at the continuation call site (file offset `0xcd798`, VA `0x1800ce398`): the `mov rcx,[r14]; call FUN_18004d640` pair is replaced with a `jmp` into a second code cave that reloads `[r14]`, and if null, jumps straight to the function's own shared cleanup/return label (`0x1800ce71a`) — skipping both the call *and* the unconditional post-call dereference, so the caller-side crash is also eliminated, not just delayed by one instruction.
  - Both caves live in real, unused space: 452 bytes of zero-padding between `.text`'s `VirtualSize` and `.rdata`'s file offset (file offset `0x176c3c`–`0x176e00`), which is mapped executable since it's part of the same PE section — no new section needed, no relocation-table changes needed.
  - Verified byte-for-byte at each step with `objdump -D -b binary -m i386:x86-64 --adjust-vma=<text_vma-text_fileoff>` before ever testing live — this caught a real bug in the first attempt (a naive entry-patch that skipped the original prologue pushes on the *valid*, non-null path too, corrupting the stack for every normal call and immediately manifesting as `err:seh:call_seh_handlers invalid frame` / `NtRaiseException ... unable to dispatch exception`).
  - **A retry-with-`Sleep(1)` variant was also tried** (spin up to 30× `Sleep(1)` via the DLL's own imported `Sleep` IAT slot, `CALL qword ptr [0x180178108]`, before giving up and treating it as truly malformed) on the theory that the null was a short-lived scheduling race — this made no measurable difference (the "no response ever arrives" cases below aren't a short race), so the simpler drop-and-cleanup version is what's kept.
  - **Result: verified crash-free across 5+ consecutive fresh launches** under real (elevated) system load, vs. 2/2 guaranteed crashes at the identical instruction immediately beforehand. This is a real fix to Hotone's binary, not a probability-reducing Wine-side workaround — should hold regardless of Proton/esync/scheduling behavior.
- **Distribution note**: patching `HTUSBTools.dll` (Hotone's proprietary binary) is legally different from patching Wine (LGPL) — a redistributable release should ship this as a binary diff/patch script applied to the user's own legitimately-installed copy, not a pre-patched DLL file.

## Bug #5 — RESOLVED (2026-07-27): app sometimes never left "No Device Connected" — root cause was our own throttle "optimization" from earlier in this session, not the pedal
**TL;DR: don't touch the `usleep(30000)` in `handle_sysex_event()` — it must fire unconditionally on every buffer completion (both real 0xF7 ends *and* buffer-full mid-message splits), not just on real message ends. An "obvious" optimization to only delay on real ends was tried and is a severe regression, confirmed by directly regression-testing saved binaries against each other.**

- With Bug #4 genuinely fixed (crash-free, see #4b), this became the last blocker: the app stayed alive but stopped receiving further MIDI data partway through the startup handshake (`5000017` → `3800`×5 → `90000` → `1000000` → `3000001` → `1080000` → ...), staying on "No Device Connected" forever.
- **Extensive diagnosis initially pointed at the pedal itself**: `aseqdump` and `WINEDEBUG=+midi` tracing showed our outgoing requests going out correctly with nothing coming back; kernel-level `usbmon` packet capture (root via a graphical `pkexec` prompt — see security note below) showed the raw USB bulk-IN endpoint going completely silent, with the kernel's URB seemingly never completing again. This looked exactly like "the pedal's firmware stopped responding" and was very hard to distinguish from a real hardware issue — A/B tests against a brand-new never-crashed prefix and the original unpatched `HTUSBTools.dll` both reproduced the identical stall, which (wrongly, as it turned out) seemed to rule out anything on our own code.
- **What actually broke it, found by direct regression-testing saved binaries against each other** (prompted by the user correctly refusing to accept "it's the pedal's fault" when the exact same setup had worked earlier the same day): early in this session, `handle_sysex_event()`'s post-notification `usleep(30000)` was changed from firing **unconditionally on every buffer completion** (both a genuine `0xF7` end-of-message *and* a buffer-full mid-message split) to firing **only on genuine message ends** — reasoning at the time was that delaying on a buffer-full split was "wasted" since the app can't process an incomplete message anyway. This looked like a strict improvement and was carried through several further variants (100ms, then adaptive 30–300ms scaled by message size, then removing the delay entirely when it still didn't help) — **every single one of these variants regressed reliability**, all dying somewhere in the same address range, compared to the original.
- **Proof**: saved compiled `winealsa.so` copies exist for every variant tried this session in `/home/deck/ampero_editor/binary_versions/winealsa_so/` (v0 vanilla, v1 = today's earlier known-working build, v2 = conditional 30ms, v3 = conditional 100ms, v4 = adaptive, v5 = no delay, v6 = restored-and-current). Swapping **only** `v1`/`v6` (unconditional throttle) back into the live Proton install, with everything else identical (same prefix, same pedal, same low system load, same htusbtools.dll patch), took the app from reliably dying around `0x100000`–`0x1080000` to **reliably reaching the full working editor UI, 3/3 consecutive runs**, sailing straight through many more handshake addresses (`3000005`, `a0000`, `4000003`, `10a0003`, etc.) that no other variant had ever reached.
- **Mechanism is not fully understood** (this is the honest caveat) — the ALSA-sequencer-queue-starvation theory used to justify removing the delay entirely turned out to be wrong or at least incomplete, since *more* total delay (firing on every chunk, not fewer times) is what actually helps. Best current guess: pacing is needed between every raw chunk handoff to the app, not just at logical message boundaries — possibly because Hotone's own reassembly code (or the pedal's USB controller) needs breathing room between *every* delivered chunk of a burst, not only between distinct messages. Filed as an open question, not re-investigated further this session given the fix is verified and reliable.
- **Fixed**: restored the unconditional `usleep(30000)` in `/home/deck/wine-src-11.0/dlls/winealsa.drv/alsamidi.c`, with a comment warning future sessions not to "optimize" it again without re-running this same regression test. Rebuilt and reinstalled into Proton's `winealsa.so`.
- **Lesson for future sessions**: when regression-testing timing-sensitive native code, save every intermediate compiled binary (not just source diffs) as you go, so a direct binary-swap A/B test is always possible without a rebuild — this is what finally cracked it. `/home/deck/ampero_editor/binary_versions/` now holds these for both `winealsa.so` and `HTUSBTools.dll`; keep adding to it if this code changes again.
- **Security note for future sessions**: while investigating this (before the real cause was found), the user typed their sudo password directly into the chat as plaintext at one point, while trying to grant `usbmon` access. That password must be treated as compromised (it's preserved in conversation history) — **do not** repeat this; the correct way to get a one-off privileged command run is `pkexec <command>`, which pops a native graphical polkit password dialog that never touches the chat/conversation log at all.
- The `community.hotoneaudio.com` HTTPS GET request and the pedal's USB-level firmware were both investigated as candidate causes and are **not** the issue — see git history of this file if the full (now-obsolete) diagnostic trail is ever needed.

### Bug #5 follow-up (2026-07-27, second machine — KDE neon 24.04/Ubuntu noble, AMD RADV): three parts of the description above were still wrong
The `full_bundle/` was handed to a second machine for a clean portability test. Full detail in `full_bundle/INVESTIGATION.md`; summary:
- **Not "one specific address"**: over 70 instrumented launches, stalls landed on `1080000` (most often), `1000000`, and `300000a`.
- **The pedal is not at fault, confirmed a second way**: decoding the SysEx address out of `aseqdump` captures (framing: after the `F0 21 25 4D 50` header, byte 3 is `0x11`=request/`0x12`=reply, bytes 9-15 are a 28-bit address as one nibble per byte, little-endian) and matching requests to replies shows the pedal's reply is **on the wire in full, correctly framed**, for every stall examined. ALSA is also clean (`Alloc failures: 0`, no rawmidi overruns, Wine keeps recycling buffers). **So the reply is lost above ALSA — in Wine's MIDI-in path or in the app itself**, which queues input in only 112-byte buffers. This is the one part of Bug #5 that is still genuinely open.
- **Not "connects within 1-2 tries essentially always"**: measured per-launch success rate drifted between ~20% and ~90% over tens of minutes, for reasons that were not pinned down (six single-variable theories — MIDI tracing overhead, a second ALSA-seq subscriber, background CPU load, idle C-states, seq-pool overflow, the mid-handshake HTTP call — each looked significant in one paired series and then failed to replicate; treat the mechanism as genuinely unknown, and always A/B two configurations by alternating single trials rather than comparing two series run at different times).
- **Workaround shipped in `full_bundle/launch.sh`**: watches the app's log for the `EffectChain Refresh` success marker and for silence on the `请求命令地址` request-log line (15s with no new request = stalled), and relaunches via `wineserver -k` + retry, up to `AMPERO_ATTEMPTS` (default raised from 6 to 10 after the wrapper was observed exhausting 6 in a bad window). This is a workaround, not a fix.
- **Instrumentation fix (2026-07-27, this session)**: the rebuilt `winealsa.so` already had unconditional SysEx-chunk tracing (`trace_sysex_chunk()` in `alsamidi.c`) writing every chunk Wine's driver receives to `/tmp/wine_midi_trace_proton.log` — but the second machine's tester assumed it was gated behind `WINEDEBUG` (it isn't; it's a plain unconditional `fopen`/`fprintf` to a hardcoded path) and never found it, calling the missing rebuild source a "blocker". It isn't a blocker: the trace file appears on **any** machine that runs this `winealsa.so`, no source needed, no `WINEDEBUG` flags needed. Confirmed the mechanism works — `/tmp/wine_midi_trace_proton.log` already had 1430 lines of real data from earlier the same day on this machine. **Added wall-clock timestamps to each trace line** (`clock_gettime(CLOCK_REALTIME, ...)`, commit `7619394c`) so a stall's trace entries can be matched against a timestamped wire capture (`aseqdump`) after the fact without having to guess process/launch boundaries. Rebuilt and reinstalled into both the live Proton and `full_bundle/`.
- **Fork closed (2026-07-27, same session): the app is dropping it, not Wine.** Ran a timestamped `aseqdump -p 20:0` capture in parallel with the app on this machine, launching repeatedly until a real stall hit — attempt 2 stalled on `1080000` after 10 requests. Decoded both the wire capture and `/tmp/wine_midi_trace_proton.log` for the stall window (`decode_stall.py`, folded into `tools/match-replies.py`): **all 20 SysEx messages in the window, including the `0x1080000` reply itself, match byte-for-byte and timestamp-for-timestamp between the wire and what Wine's driver assembled and handed to the app** (see raw comparison in git history of this file / the session transcript if needed). Wine did not drop, truncate, or delay anything relative to the wire. Since the app never issued request #11 despite having been handed a complete, correctly-framed reply, **the drop is inside Hotone's own compiled Dart/Flutter code** — most likely an exception or a stuck await in its MIDI-input callback handling for that specific reply, analogous in kind to Bug #6 (also a silent failure in `mp380`'s own Dart code, also not something we can binary-patch the way `HTUSBTools.dll` was). Going further (isolating exactly which byte/field trips it) would mean reverse-engineering the AOT-compiled Dart app itself, a materially bigger undertaking than the native-code work done so far — not attempted this session pending explicit direction to pursue it.
- **Practical conclusion**: the shipped `launch.sh` retry-wrapper (relaunch on stall) is not a stopgap pending a real fix — it is, as far as this investigation can tell without decompiling Hotone's Dart app, the correct and complete mitigation available to us. Six single-variable theories for *why* the drop rate drifts 20-90% were tried and rejected (see the follow-up note above); none of them, nor this new wire-vs-Wine proof, points at anything left to fix on the Wine/ALSA/native side.
- Still worth doing if anyone picks this up again: A/B the rebuilt `winealsa.so` against the stock `winealsa.so.orig-backup` kept beside it in `full_bundle/proton/lib/wine/x86_64-unix/` (never done — the rebuild was never actually the suspect, but it's a cheap check to rule out entirely).

### Bug #5 follow-up 2 (2026-07-27, same session): gdb'd a live stall's thread stacks — a real X11 deadlock exists, but disabling it doesn't fix the connection rate
With a wire-vs-Wine proof already in hand pointing at the app, went one level deeper without touching Dart: caught a live stall (again on `1080000`), used `pkexec gdb -p <pid> -batch -ex "thread apply all bt"` to dump every thread (ptrace needs root here — Wine reparents the actual game process away from the launching shell, so it isn't a ptrace-able descendant under the default Yama `ptrace_scope=1`).
- **The app's own log goes completely silent the instant it requests the address that stalls** — not just "no reply for that one address", *zero* further lines of any kind (no error, no next request). This pointed at a hang, not a one-message silent-drop.
- **Thread 1 (main thread, "Ampero II.exe") was frozen inside `winex11.so`'s `use_kwin_hacks()` → `X11DRV_HasWindowManager()` → `XQueryExtension`/`_XReply`/`xcb_wait_for_reply64`** — a synchronous X11 server round-trip — called from `X11DRV_WindowPosChanged` → `update_net_wm_states`, itself called from `NtUserSetWindowPos` while processing a message inside `NtUserGetMessage`, i.e. **the same thread that pumps the Win32 message queue that MIDI-input callbacks are dispatched through**. If this thread is blocked, the app cannot process a newly-arrived MIDI message no matter how correctly Wine delivered it — consistent with everything observed.
- `use_kwin_hacks`/`X11DRV_HasWindowManager` are Proton-specific (not in vanilla wine-11.0 — not present in our `wine-src-11.0` checkout at all, only in Proton's own patched `winex11.so`), gated by an env var found via `strings`: `WINE_USE_KWIN_HACKS`.
- **Tested it properly**: `tools/handshake-trials.sh -n 12 nokwin plain` (alternated trial-by-trial, per the anti-drift methodology). Result: `nokwin` 7/12, `plain` 8/12 — no significant difference, within noise. **Rejected.** Either the env var only changes behavior *after* this particular X11 round-trip (doesn't skip the call itself), or the gdb snapshot caught a real-but-unrelated coincidence rather than the actual cause. Not distinguished — the honest state is "found a genuine Wine/X11-level deadlock candidate, disproved the one available env-var mitigation for it, did not chase it further" (would need e.g. two snapshots of the same frozen process seconds apart to confirm it's truly wedged forever vs. just slow, then digging into why `XQueryExtension` blocks — possibly Xlib/xcb thread-safety with DXVK's own X11/Vulkan WSI thread sharing the same display connection).
- **This is now the seventh single-variable theory tried and not surviving a controlled re-test** in this investigation (see the list in the earlier follow-up note) — treat any new one-off theory about this bug with the same skepticism until it's alternated-trial tested.

### Bug #5 follow-up 3 (2026-07-27, same session): two-snapshot confirmation — real freeze, but NOT a native deadlock
Per the user's request, re-ran the catch-a-live-stall test but took **two** `pkexec gdb` thread-backtrace snapshots of the same frozen process 6 seconds apart, to tell a genuine permanent freeze apart from "just caught a slow call". Caught another stall on `1080000` (10th attempt this run).
- **This time the main thread was NOT inside `use_kwin_hacks`/X11 at all** — it was sitting in a completely normal, healthy `NtUserGetMessage` idle wait, in *both* snapshots. This directly confirms the earlier X11-deadlock sighting was coincidental, not causal (consistent with the `nokwin` A/B test result above) — same stall address, completely different main-thread state.
- **Diffed all ~47 threads between the two snapshots**: every single one — the main thread, both Flutter engine thread pools (`io.flutter.ui`/`rast`/`io`, `io.worker.*`), Wine's `mmdevapi_midi_n` notify thread, the ALSA driver's own `rec_thread_proc` — has a **byte-for-byte identical stack, same addresses, 6 seconds apart**. The only thread that changed at all was DXVK's own Vulkan presentation-wait thread cycling between its normal internal states (expected background GPU activity, unrelated).
- **Conclusion**: the freeze is real and sustained, not a mis-caught slow call — confirmed. But it is **not a classical OS-level deadlock**: no thread is blocked trying to acquire a lock held by another blocked thread; every thread is parked in an otherwise-healthy "wait for an event" primitive (`poll`, `pthread_cond_wait`, `NtWaitForAlertByThreadId`) that would resolve fine if something signaled it. Nothing is stuck *waiting on* anything identifiable at the OS/thread level — the entire process has simply gone quiet, with no thread scheduled to do more work. This points at a **pure Dart-level control-flow bug** (an `await` that never resolves, an exception swallowed by a catch-all, a sequence/state check that silently fails to schedule the next step) rather than anything native-debuggable further. This is the ceiling of what native-side tooling (gdb, Wine instrumentation) can tell us about this bug — going further needs Dart AOT reverse engineering, not attempted.

## Bug #7 — FIXED (2026-07-27, found on second machine): bundled Proton always re-execs the 32-bit loader, even for this pure-64-bit app
On a host with no i386/multilib runtime at all (KDE neon 24.04 shipped none), `full_bundle/launch.sh` died instantly with `/lib/ld-linux.so.2: could not open`, before any Wine output. `strace` showed why: `proton/bin/wine` (the 64-bit binary) unconditionally re-execs into `proton/lib/wine/i386-unix/wine-preloader` before doing anything else — this is how an **old-style WoW64** Wine build works (`lib/wine/i386-unix/ntdll.so` exists, so the 32-bit loader is the canonical entry point), and it happens even when the target executable is pure x86-64 (`Ampero II.exe` is `PE32+ x86-64` — the 32-bit half was never actually needed for this app). Fix: in `launch.sh`, when no i386 `ld-linux.so.2` is present on the host, drive `proton/lib/wine/x86_64-unix/wine64` directly with `WINELOADERNOEXEC=1`, which skips the re-exec/preloader step entirely (`WINELOADER` alone does not help — the re-exec still happens). On a host that does have 32-bit glibc (SteamOS included) the original code path is unchanged. Also confirmed: `winedmo.so` fails to load on hosts with FFmpeg 5+ (linked against the FFmpeg-4-generation `libavcodec.so.58`/`libavformat.so.58`/`libavutil.so.56`, not shipped in the bundle) — harmless today since the app never touches Media Foundation, but worth knowing if that ever changes. Full writeup: `full_bundle/INVESTIGATION.md`.

## Bug #6 — ROOT-CAUSED, not fixed: dropdown/list overlays never render their content
- Discovered while manually testing the working UI: in "Global Settings" pages, dropdown widgets (Language, Display Time, LED Strip, etc.) visually open (a black popup box appears on click) but never show their list items — confirmed this is **not** an input or general-rendering problem: clicks register correctly and the underlying setting actually changes when clicking where an (invisible) item would be. Regular non-overlay widgets (color swatches, radio buttons like Mode 1/Footswitch) render and work perfectly.
- **Root cause found directly in the log** (captured via redirecting `stdout`/`stderr` — Flutter prints uncaught Dart exceptions there): every time a dropdown opens, this fires once per list item —
  ```
  [ERROR:flutter/runtime/dart_vm_initializer.cc(41)] Unhandled Exception: Null check operator used on a null value
  #0  State.setState (package:flutter/src/widgets/framework.dart:1159)
  #1  _ListViewCellState.initState.<anonymous closure> (package:mp380/Views/Global/widgets/listViewCell.dart:34)
  ```
  This is a genuine, unhandled Dart exception in the app's own compiled code (package `mp380`, file `Views/Global/widgets/listViewCell.dart` line 34) — some value the cell's `initState` unconditionally null-asserts (`foo!`) is actually null in this environment. Because it throws during `initState`, the cell's visual content is never built, but the enclosing list item's hit-test/tap-handling machinery is apparently set up independently and still works — matching the observed "invisible but clickable and functional" behavior exactly.
- Investigated one candidate cause and ruled it out: `RtlGetThreadPreferredUILanguages` is a Wine stub (`fixme:nls`, "returning a dummy value") that fires around the same time, but it does return a validly-formatted (if minimal) single-language response, so it's likely coincidental rather than the actual null source.
- **Confirmed scope, empirically**: this only affects dropdowns in the "Global Settings" pages (Language, Display Time, LED Strip, etc.) **on V1.0.0**. Dropdowns/lists elsewhere — e.g. the effect-chain's cabinet/model selector — render their content perfectly fine, and opening one produces **zero** `Unhandled Exception` log lines, confirming those use a different code path from `_ListViewCellState`.
- **Ruled out**: DWM blur/acrylic backdrop effects (Wine stubs, a plausible cause for exactly this "container renders, content doesn't" symptom) — the app never calls `DwmEnableBlurBehindWindow`/`DwmSetWindowAttribute` in this session. Web search found no existing documented case matching this exact symptom either.
- **UPDATE — moot in practice, confirmed with a screenshot**: tested on **V1.5.1** (the actual current release) with the same full fix set — the "Instrument" filter dropdown in the Hotone Community browser opened showing fully legible content ("Acoustic Guitar" / "Electric Guitar" / "Electric Bass"). Global Settings dropdowns, Community browsing/filtering, everything rendered correctly. So this bug is specific to the older V1.0.0 UI code and doesn't affect the version anyone would actually use. Not pursued further.
